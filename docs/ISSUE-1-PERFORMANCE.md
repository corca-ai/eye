# Issue #1 비용 최적화 검증 기록

이 문서는 [이슈 #1](https://github.com/corca-ai/eye/issues/1)의 구현·측정 기록이다. 합성 workload의 검증이며 개별 서비스의 운영 도입 승인을 뜻하지 않는다. 과거 v1 비용 추정과 분리한다.

## 원격 학습 기준선 (2026-10-24)

- v2 선행 커밋: `69902c4`. 측정 전 Basin의 최대 LIMIT에 맞춰 원본 조회를 `LIMIT 10000` / 허용 9,999행으로 보정했다. 초과 응답은 성공으로 취급하지 않는다.
- 별도 시험 배포 `eye-i1-20261024`: 기존 서비스 리소스를 변경하지 않았다. `cf`로 배포했다. CLI의 `sql query`는 `/analytics/sql`이며 Basin warehouse 조회가 아니므로 학습 및 EXPLAIN은 공식 Basin SQL HTTP API를 사용했다.
- 재현: `benchmarks/cf-load/cohort-bench.mjs baseline --seed`, 수집 가시성을 확인한 뒤 `cohort-bench.mjs baseline`. 인증과 고정 fixture는 git에서 제외된 `.state`에, 원시 결과는 `results`에 보관한다. 동일 fixture를 최적화 후에도 사용한다.
- 100명, 3개 실험, 실험당 3개 arm, 표본당 실제 노출 3회. 노출 900건, 일반 track 4,000건, 신원 연결 25건, 양수/음수 골 240건: 총 5,165건, 마감 표본 300개. 사용자 절반은 uid를 직접 제공하며 첫 로그인·다른 기기 구매도 포함한다. 골이 없는 사용자도 포함한다.
- 관측 기간 7일, 학습 마감 유예 1시간. 과거 발생 사건을 현재 수집해, 발생 시각과 수집 파티션 날짜가 다른 조건을 검사한다. 파일 rollover는 60초다.

|---|---:|
| 학습 SQL | 13회 (50개 표본 × 6페이지의 2쿼리 + 마지막 빈 조회) |
| 전체 HTTP 처리 시간 | 30,933ms |

이는 작은 정확성 fixture의 1회 측정이다. p95나 운영 규모 처리량으로 해석하지 않는다. 최소 과금 스캔량, 캐시 효과, Catalog/R2 작업과 수집 비용을 별도로 적용해야 한다. 쿼리 수의 감소율을 그대로 총 비용 감소율로 주장하지 않는다.

실제 Catalog metadata에서 events의 `__ingest_ts`에 대한 DAY 파티션을 확인했다. 발생 시각만으로 이 파티션이 잘린다고 가정하면 늦게 수집한 과거 사건을 잃는다.

두 종류의 쿼리 모두 원격 EXPLAIN이 HTTP 200으로 성공했다. 대상 선택 쿼리는 `payload_json`에서 sample ID/마감 시각을 추출하고 Window/Sort를 수행한다. 일반 track까지 들어 있는 사건 테이블을 반복 읽는 구조다. 원시 실행 계획은 `results/baseline-explain-{0,1}.json`에 있다.

## 구간 SQL 시험

동일 fixture를 저장소에서 귀속·정규화 합산하도록 한 단일 SQL 시험은 HTTP 200, 300표본, 보상 불일치 0이었다. 3,179ms, `bytes_scanned` 1,532,530, `files_scanned` 25, `r2_requests_count` 94였다. 기존 13쿼리 대비 스캔 바이트 감소는 약 35%이며, 단일 실행의 시간 차이를 일반적인 성능 보장으로 취급하지 않는다. 실제 LearningSource 연결 후 원격 재검증도 1쿼리·300표본·보상 불일치 0으로 통과했다. 해당 HTTP 실행은 4,242ms였고 스캔량·파일 수·R2 요청 수는 SQL 시험과 같았다. 이후 용량 초과 재시도 분류 변경은 로컬 테스트로 검증했으며 원격 alarm 재시도 검증은 남아 있다.

두 리뷰어가 발견한 반복 sample 문맥 충돌 검사를 추가한 최종 SQL도 원격 HTTP 200·300표본·불일치 0으로 통과했다. 이 검사로 스캔량은 1,800,198바이트(기준선 대비 약 24% 감소), 파일 수 27, R2 요청 수 106이 되었다. 위 35% 절감은 검사 추가 전 시험값이며 최종 수치로 사용하지 않는다. 최종 전체 HTTP 지연은 이후 부하 검증에서 다시 측정한다.

## Queue 묶음 처리

같은 ingest 호출 안의 일반 이벤트는 60,000바이트/100건 이내 메시지에 묶는다. 기존 SDK 한도 내 큰 이벤트는 단독 메시지로 보낸다. 호출 사이에 묶음을 기다리지 않는다. 작은 사건이 평균 k개씩 모이면 메시지 수가 대략 1/k로 줄지만, 실제 과금은 크기 단위·재시도·트래픽에 따라 달라진다. 원격 요청 지연은 아래 부하 시험, 가정별 총비용은 [v2 비용 모델](COST-V2.md)을 따른다.

타입 검사와 집중 테스트 8개가 통과했다. 두 독립 리뷰어가 기존 SDK 한도와의 불일치를 발견했고, 큰 이벤트의 단독 전송 및 형제 이벤트 보존 회귀 테스트로 수정한 뒤 두 리뷰어의 재확인을 받았다.

## 운영자 비동기 조회

동일 fixture의 골 집계를 비동기 작업으로 원격 실행했다. 동시에 보낸 동일 요청 두 개가 같은 job ID를 반환했고, 결과 완료 후 다시 등록해도 같은 ID를 재사용했다. attempts=1, 골 240건과 가치 합계가 fixture와 일치했으며 스캔량은 135,526바이트였다. 최초 두 등록을 기다린 외부 시간은 2,161ms, 상태 폴링·결과 조회·캐시 재등록까지 전체 7,724ms였다. 단일 cold 측정이며 사용자 선택 경로 지연을 측정한 값이 아니다. 재현 명령은 `node benchmarks/cf-load/operator-bench.mjs`다.

로컬에서는 권한 scope·사이트별 격리, 객체 재시작 후 R2 결과 재사용, 취소 중 게시 방지, 결과 페이지 재사용, 만료, 재시도 한도를 확인했다. 이 단계 전체 검사 118개와 외부 패키지 검사가 통과했다.

## 분석 SQL 원격 호환성

실제 Basin에서 cid/uid 타임라인과 `hasEvent` arm 조회를 확인하면서 로컬 SQLite에서는 드러나지 않던 오류를 수정했다. 엔진의 `__ingest_ts`가 UNION 컬럼 수를 바꾸지 않도록 wire 컬럼만 선택한다. 타임라인은 각 branch가 `(table_name, record_id)`로 유일하므로 UNION으로 같은 행 집합을 유지하며 Basin의 UNION ALL 분산 실행 오류를 피한다. 로그인 구간은 독립 CTE에서 계산하고 이벤트 조건은 JOIN 안의 상관 서브쿼리를 피한다.

같은 fixture에서 최종 uid 타임라인은 HTTP 200·11행(10행 한도와 다음 페이지 확인용 1행), 795,806 스캔 바이트였다. `hasEvent: page_view` arm 조회는 HTTP 200·3행, 798,586 스캔 바이트였다. 이 수치는 기능 호환성 확인이며 최적화 전후 비교나 p95 측정이 아니다. 로그인 반복·계정 전환·로그아웃·동일 시각 ID 순서는 로컬 `IdentityHistory` 기준과 비교한다.

## 노출 projection 전송 축소

노출의 pending 관측과 selected 배정은 원본에서 조회 시 재구성하고, 학습이 확정한 complete 관측은 계속 저장한다. 최초 전송만을 특별 취급하지 않으므로 후속 노출만 남아도 표본이 복구된다. 별도의 사용자 원장은 없다. 기존 물리 projection과 새 원본을 함께 조회하는 전환 계약은 [분석 문서](ANALYTICS.md#projection-전송-축소-버전으로-전환)에 있다.

위 5,165사건 fixture를 같은 수신 시각으로 인코딩하고 실제 `exportBatches` 한도를 적용한 결과, 전송량은 9,431,653 → 7,111,389바이트(약 24.6% 감소), 레코드는 7,018 → 5,211개였다. 노출 900건의 pending 900행·selected 900행 전송이 사라지고 배치 수에 따른 속성 사전 중복도 줄었다. 이는 원본 이벤트와 골을 모두 보존한 인코딩 비교이며, 실제 Queue 배치 구성에 따라 사전 중복과 총 바이트는 달라진다. 조회는 원본을 더 읽으므로 이 비율을 총 비용 절감률로 해석하지 않는다.

재현용 `node benchmarks/cf-load/projection-bench.mjs --seed`는 별도 테스트 site에 새 형식만 수집한다. 반영 후 같은 명령에서 `--seed`를 빼면 pending·배정·노출 수와 uid 타임라인을 확인한다. 이전 fixture의 물리 projection 때문에 테스트가 우연히 통과하지 않도록 site를 분리했다. 실제 Basin에서 exp-0의 pending 100·배정 100·노출 300과 user-0 타임라인의 관측 3·배정 3이 모두 일치했다. arms/traffic/timeline 스캔은 각각 942,600/352,417/1,363,094바이트였다. 기존 시험과 파일 구성이 달라 직접적인 전후 스캔 비교는 아니다.

## 확정 학습 요약과 자동 보고서

`analytics.learning()`은 확정 complete 관측만 읽으며 원본 귀속을 다시 계산하지 않는다. `jobs.schedule/scheduled/unschedule`은 골·학습 기본 보고서만 opt-in으로 자동 생성한다. 등록·읽기·취소·보관·범위·보상 의미는 [분석 문서](ANALYTICS.md#기본-보고서-자동-생성)를 따른다.

`node benchmarks/cf-load/scheduled-bench.mjs --publish`로 fixture의 마감 관측 300개를 내보낸 뒤 가시성을 확인하고, `--publish` 없이 실제 alarm 실행을 검증했다. 자동 학습·골 보고서 모두 attempts=1, 완료 표본 300개·골 240개가 일치했다. 학습 보상 합계는 reducer와의 차이가 약 3.64e-12로 허용 오차 1e-8 안이었다. 동일 일정 재등록이 같은 결과를 유지했고 저장 페이지 이동은 새 SQL 작업을 만들지 않았다. 검증 일정은 종료 시 삭제했다.

확정 학습 요약(사이트 전체 3실험)은 66,131바이트를 스캔했고 원본 귀속 arm 조회(1실험)는 776,603바이트였다. 서로 다른 의미·범위의 API이므로 동일 기능의 전후 성능 비교로 주장하지 않는다. 기본 화면이 확정 학습 결과로 충분하면 전자의 작은 결과를 재사용할 수 있다. 원본 기반 ad hoc 분석은 계속 제공한다.

로컬에서는 재시작·일정 재등록·설정 변경·삭제 후 재생성 경쟁·권한 scope·대기열 포화·실패 시 이전 결과 보존을 확인했다. 원격에서는 최초 alarm 실행을 검증했으며 한 시간 간격의 반복 실행을 실제로 기다린 시험은 아니다.

## 학습용 읽기 경로 선택

같은 fixture에서 bulk SQL의 event 입력을 필요한 컬럼 목록으로 제한하고, experiment_id/goal_id 조건을 추가하는 시험을 했다. 300표본의 문맥은 같고 보상 차이는 최대 약 1.42e-14였지만 스캔은 1,918,882 → 1,930,816바이트로 줄지 않았다. 실행 시간 단일 관측(2.35 → 1.72초)은 캐시·서버 변동을 분리하지 못하므로 속도 개선으로 주장하지 않는다. 추가 조건이 이 workload의 스캔 비용을 줄이지 않아 적용하지 않았다. 증거는 `results/learning-narrow-comparison.json`이다.

현 단계에서는 새 학습용 물리 테이블을 기본으로 추가하지 않는다. 노출·골을 다시 내보내는 비용과 스키마 전환 복잡성을 확실한 절감 근거 없이 늘리지 않기 위해서다. 구간 단위 학습과 확정 관측만 읽는 기본 보고서를 사용하고, 큰 payload가 지배적인 서비스에서는 별도 projection의 실제 전송·스캔 합계를 다시 측정한다.

## 파일 생성 간격 60초/300초 비교

기존 60초 events/identity sink를 보존하고 같은 Stream을 읽는 `eye_roll300` 네임스페이스의 300초 sink를 추가했다. 1분 간격 6배치, 총 6,990사건(노출·골·신원 사건)을 전송했고 모든 배치가 보인 뒤 kind·arm·cid/uid 구분별 수가 일치했다. 각 경로에서 기본 1000표본 페이지 두 개로 학습한 결과는 1,800표본, reducer 대비 보상 불일치 0이었다. 로그인 연결과 페이지 밖 실험 분모도 동일 fixture로 검사한다.

Catalog snapshot 이력이 시험 구간 전체를 포함하는지와 추가 레코드가 정확히 6,990개인지 확인했다. 추가 events 파일은 4 → 1개, 압축 파일 크기는 289,929 → 251,495바이트였다. 첫 전송 시작에서 첫 events commit까지는 60초 경로가 약 139초, 300초 경로가 약 371초였다. 모든 사건이 조회됨을 확인한 시점은 각각 약 422초/425초였으며 마지막 배치 전송 완료로부터 약 106초/109초였다. 이 값은 해당 시험의 관측값이며 개별 사건 p95나 전달 SLA가 아니다. 파일 간격을 그대로 수집 가시성 상한으로 사용하지 않는다.

두 학습 쿼리의 스캔 합계는 9,470,952 → 7,257,130바이트였다. 기존 네임스페이스에는 이전 시험의 metadata 이력도 있으므로 차이 전부를 파일 간격 효과로 돌리지 않는다. 기존 events 테이블은 Catalog가 관리하는 128MB·1시간 간격 compaction이 활성화되어 있었고, 위 파일 비교는 snapshot의 append 집계다. 압축 후 파일 수 감소를 총 청구액 감소율로 사용하지 않는다.

재현: `roll-provision.mjs` → `roll-bench.mjs --seed` → 반영 후 `roll-bench.mjs`, `roll-snapshots.mjs`, `roll-learning.mjs`. 원시 결과는 `results/roll-*.json`이다. 신규 설치는 300초를 기본으로 하고 기존 설치는 자동 변경하지 않는다. 기본 학습 유예 1시간은 변경하지 않았으며 짧은 유예는 별도 측정과 설정이 필요하다.

자동 invocation 로그는 비활성화하고 명시적 진단 로그는 sampling 1로 유지한다. 이는 원본 사건 샘플링이 아니며, 실제 로그 청구 절감액은 요청 부하 검증에서 별도로 확인한다. `cf workers get`으로 배포된 Worker의 logs.enabled=true, head_sampling_rate=1, invocation_logs=false를 확인했다.

## 검증 범위

구간 단위 학습·비동기 조회·반복 projection 제거·정책 신선도 분리·수집 묶음·파일 생성 간격과 로그 설정을 구현하고 아래 범위에서 검증했다. 귀속·신원 경계·0/음수/큰 보상·분할·재시도는 reducer 비교 및 로컬 runtime 테스트, Basin SQL·정책 변경·학습 alarm·보고서는 원격 fixture, 요청 지연과 수집 품질은 부하 시험을 사용한다. 장기 운영·모든 계정의 지연 SLA·임의 데이터 분포의 월 비용을 증명한 것은 아니다. 원본 보관량과 운영자 조회량에 따른 총 비용은 명시적 가정별 모델로 제공한다.

## 속성 사전 확장 후 전송 크기 제한

연결된 [이슈 #3](https://github.com/corca-ai/eye/issues/3)을 현재 후보에서도 재현했다. SDK가 수락한 10,000개 scalar 속성의 이벤트가 사전 행으로 확장되면 하나의 전송 한도를 넘었고, 앞뒤 정상 사건까지 같은 Queue 처리가 실패했다. ingress 바이트 제한을 줄이지 않고, 확장된 wire 레코드 단위로 JSON 배열의 구분자까지 포함해 4,500,000바이트 이내로 나눈다. 확장·크기 계산을 한 번 수행하고 이미 확장한 결과를 Stream에 직접 보낸다.

실제 SDK 수락 → Queue consumer → Stream 대역을 연결한 회귀 시험에서 원본 3개·속성 키 10,000개가 모두 보존되고 각 전송의 UTF-8 크기가 한도 이하임을 확인했다. 두 번째 전송에 실패를 주입하면 원본 메시지 전부가 재시도되고, 재실행에서 정상적으로 완료된다. 전체 사건의 ACK는 모든 전송 성공 후에만 실행한다. 재시도는 같은 record ID를 사용하므로 분석의 중복 제거 계약을 유지한다. 이는 로컬 runtime 검증이며 원격 장기 DLQ 시험을 했다는 뜻은 아니다.


## 상태를 유지하는 10·100·200 RPS 요청 시험

2026-10-24, `stateful-1792822068189-7bb04469`에서 1분 예열 후 각 부하의 baseline/Eye를 5분씩 순차 실행했다. 3실험·3arm, 최소 유지 1일·관측 7일, VU별 반복 사용자와 5% 신규 요청, 익명/로그인 사용자, 양수·음수 골을 포함한다. `/fast-page`는 사용자 상태를 요청 헤더로 전달하고 정책 조회와 수집을 기다리지 않는다. 응답은 두 모드 모두 8192바이트다. 이 시험은 최적화 전 v2와 최적화 후의 비교가 아니라 **동일 호스트의 Eye 미사용/사용 비교**다.

미참여율의 분모는 HTTP 요청 수가 아니라 실험 결정 수다. 예를 들어 후속 200 RPS 시험은 60,001요청의 180,003결정 중 1,166결정이 미참여였다.

| RPS | baseline p50 / p95 / p99 (ms) | Eye p50 / p95 / p99 (ms) | Eye 실험 결정별 미참여율 |
|---|---|---|---:|
| 10 | 292.37 / 1262.08 / 1884.79 | 511.29 / 1326.06 / 2091.82 | 0.0333% |
| 100 | 232.10 / 1156.75 / 1670.83 | 407.73 / 1129.36 / 1538.84 | 0.0367% |
| 200 | 174.08 / 1063.73 / 1425.38 | 193.78 / 1099.56 / 1517.18 | 0.5517% |

위 수치는 단일 지역 생성기의 전체 응답 지연이다. 순차 시험의 네트워크 시간 변동과 상태 헤더 차이를 포함한다. TTFB p50은 각각 baseline/Eye 226.19/231.37, 194.15/209.28, 167.87/184.93ms였다. 전체 응답 p50 증가를 모두 SDK CPU 비용으로 돌리거나 지연이 없다고 주장하지 않는다. 10·100 RPS에서 호스트 평균 CPU는 baseline 약 0.56/0.57ms, Eye 약 2.87/2.40ms였다. 계측 창 경계의 요청 수 차이를 포함한 Cloudflare 집계이며 개별 요청의 paired CPU 차이는 아니다.

10·100 RPS Eye의 수락 사건 12,368/123,438건은 저장소 집계와 일치했고 9개 arm과 익명/로그인별 노출 수도 일치했다. 원래 200 RPS 시험에서는 60,001요청 중 전송 timeout 1건이 발생해 당시의 엄격한 상태 검사로 실행이 실패했다. 수신한 응답의 계약 오류·수집 거부·유지 기간 중 배정/표본 변경·누락된 iteration은 없었다. 수락 응답 총계와 저장소 총계는 246,124건으로 같지만 checkout의 두 arm이 ±1건, 신원별 집계가 ±3건 달랐다. 응답 없는 요청의 서버 처리 여부를 알 수 없어 완전한 수집 일치로 판정하지 않는다.

후속 `stateful-1792824468399-70219e3c`는 최신 전송 분할 수정이 배포된 별도 사이트에서 1분 예열 후 **Eye만 200 RPS·5분** 실행했다. 60,001요청 모두 HTTP 성공이고 모든 계약 검사가 통과했다. 수락 사건 245,955건, 9개 arm별 노출 및 익명 88,288/로그인 90,549 노출이 모두 저장소 집계와 일치했다. 미참여율은 전체 0.6478%, 반복 사용자 0.6435%, 신규 0.7242%, 익명 0.6571%, 로그인 0.6386%였다. p50/p95/p99는 173.01/876.32/1292.67ms였으나 새 baseline이 없으므로 이전 시험 대비 개선 효과로 해석하지 않는다. 원래 실패 결과를 이 재시험으로 덮어쓰지 않는다.

이는 사건 ID 전체 집합 또는 arm×신원 교차 집합의 동등성 검증은 아니다. 관측 7일 설정의 짧은 부하 시험은 마감 처리를 일으키지 않으므로, 이때 SQLite rowsWritten=0인 것을 학습과 운영자 작업까지 쓰기가 없다는 의미로 해석하지 않는다. 기존 테스트 리소스의 sink rollover는 60초이고 새 설치 기본값 300초 비교는 위 별도 시험을 따른다.

### 정책 변경·속성 확장 원격 확인

`policy-1792824434102.json`은 실제 정책 RPC와 SDK runtime으로 cold 미참여, arm 중지 후 SWR 전환, 조회 실패 시 사용 기한 초과 미참여를 확인했다. 시험 설정은 fresh 250ms·최대 나이 8초이며, 중지 반영 관측은 326ms, hard expiry 이후 확인 오차는 50ms였다. 조회 실패는 adapter에 주입했다. 한 isolate에서 축소한 시간으로 검증한 값이므로 기본 15분/6시간 설정 또는 전 세계 전파의 SLA가 아니다.

전송 분할 수정 후 별도 원격 fixture에서 Stream 수락을 거쳐 Basin의 고유 원본 사건 3건과 속성 키 10,000개를 확인했다(`attributes-visibility.json`). 이 경로는 benchmark seed RPC를 사용한다. Queue의 부분 전송 실패·재시도는 위 로컬 runtime 검증이며 원격 seed가 이를 대신하지 않는다.


### 같은 시간대의 교차 비교

`stateful-1792824945407-80dd9606`에서 200 RPS·5분30초를 실행했다. 처음 30초는 예열하고, 이후 5분은 같은 사용자 상태 헤더를 보낸 baseline 30,027요청과 Eye 29,974요청을 섞었다. 두 모드 모두 8192바이트 응답이며, 상태를 확보하지 못한 신규 VU는 측정 전에 예열했다.

| 지표 (ms) | baseline | Eye |
|---|---:|---:|
| 전체 응답 p50 | 161.85 | 163.66 |
| 전체 응답 p95 | 720.35 | 716.21 |
| 전체 응답 p99 | 1137.79 | 1129.91 |
| TTFB p50 | 154.79 | 156.77 |
| TTFB p95 | 229.62 | 231.37 |
| TTFB p99 | 534.71 | 546.11 |

전체 66,001요청에서 HTTP 실패·응답 계약 오류·누락된 iteration은 0이었다. 측정 Eye 결정 89,922개 중 471개(0.5238%)가 미참여였다. 이 workload에서 p50 증분은 약 1.8ms이며, tail 차이를 통계적 개선으로 주장하지 않는다. 예열된 반복 사용자, 동일 헤더, 단일 생성기의 비교이므로 모든 서비스·지역·cold start의 지연 보장은 아니다.

앞선 `stateful-1792824857397-92b01043`의 10 RPS·45초 smoke는 측정 결정 219개 중 39개(17.8%) 미참여로 기준을 통과하지 못했다. 다른 계약 검사는 통과했다. 예열 30초·측정 15초의 이 결과도 보존하며, 200 RPS 본시험 통과를 낮은 부하의 초기 미참여율까지 해결했다는 근거로 삼지 않는다. 10 RPS의 더 긴 순차 시험 결과는 앞 표를 참조한다.


### 실제 학습 alarm의 적체 해소

`drain-1792825456676.json`은 기존 원격 fixture의 300표본이 reducer와 일치하게 조회되는 것을 먼저 확인한 뒤, 테스트 hook으로 최초 한 번 4시간 전 커서를 설정했다. 학습 실행 자체는 수정하지 않은 `SiteControl.alarm()`이다. 원격 R2 결과 고정 → ExperimentObject 통계 적용 → Stream export → 커서 전진 → 다음 alarm 예약 경로를 거쳐 4개 시간 구간을 처리했다.

초기화 이후 약 19.86초에 현재 시간 구간까지 커서가 전진하고 다음 정시 alarm을 예약했다. 9개 arm의 평균과 정책 평가 시각까지 감쇠한 표본 가중치가 기준값과 1e-8 이내로 일치했고, 마지막 학습 기준 시각도 fixture 마감 시각과 같았다. 재초기화된 시험이 아니며 10회 상태 관찰 중 미해결 오류는 없었다. 성공 시 오류 카운터가 지워지므로 폴링 사이에 복구된 오류가 전혀 없었다는 의미는 아니다.

이 결과는 비어 있는 후속 구간을 포함한 300표본 적체의 실제 처리 확인이다. 대량 적체의 최대 해소 시간이나 외부 저장소 장애 중 SLA가 아니다. 실패·부분 적용·eviction 뒤 고정 결과 재사용과 중복 학습 방지는 별도 로컬 runtime 회귀 검증을 따른다. 사용자 요청 경로는 이 학습을 기다리지 않는다.

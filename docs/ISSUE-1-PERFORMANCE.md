# Issue #1 비용 최적화 검증 기록

이 문서는 [이슈 #1](https://github.com/corca-ai/eye/issues/1)의 진행 중 측정 기록이다. 전체 작업 완료나 운영 도입 승인을 뜻하지 않는다. 과거 v1 비용 추정과 분리한다.

## 원격 학습 기준선 (2026-10-24)

- v2 선행 커밋: `69902c4`. 측정 전 Basin의 최대 LIMIT에 맞춰 원본 조회를 `LIMIT 10000` / 허용 9,999행으로 보정했다. 초과 응답은 성공으로 취급하지 않는다.
- 별도 시험 배포 `eye-i1-20261024`: 기존 서비스 리소스를 변경하지 않았다. `cf`로 배포했다. CLI의 `sql query`는 `/analytics/sql`이며 Basin warehouse 조회가 아니므로 학습 및 EXPLAIN은 공식 Basin SQL HTTP API를 사용했다.
- 재현: `benchmarks/cf-load/cohort-bench.mjs baseline --seed`, 수집 가시성을 확인한 뒤 `cohort-bench.mjs baseline`. 인증과 고정 fixture는 git에서 제외된 `.state`에, 원시 결과는 `results`에 보관한다. 동일 fixture를 최적화 후에도 사용한다.
- 100명, 3개 실험, 실험당 3개 arm, 표본당 실제 노출 3회. 노출 900건, 일반 track 4,000건, 신원 연결 25건, 양수/음수 골 240건: 총 5,165건, 마감 표본 300개. 사용자 절반은 uid를 직접 제공하며 첫 로그인·다른 기기 구매도 포함한다. 골이 없는 사용자도 포함한다.
- 관측 기간 7일, 학습 마감 유예 1시간. 과거 발생 사건을 현재 수집해, 발생 시각과 수집 파티션 날짜가 다른 조건을 검사한다. 파일 rollover는 60초다.

| 지표 | 원격 기준선 |
|---|---:|
| 학습 SQL | 13회 (50개 표본 × 6페이지의 2쿼리 + 마지막 빈 조회) |
| 전체 HTTP 처리 시간 | 30,933ms |
| 합계 `bytes_scanned` | 2,358,592 |
| 합계 `files_scanned` | 210 (동일 파일 반복 포함) |
| 합계 `r2_requests_count` | 452 (쿼리 엔진이 보고한 값) |
| 반환 표본 | 300 |
| 로컬 reducer와 보상 차이가 1e-8보다 큰 표본 | 0 |

이는 작은 정확성 fixture의 1회 측정이다. p95나 운영 규모 처리량으로 해석하지 않는다. 최소 과금 스캔량, 캐시 효과, Catalog/R2 작업과 수집 비용을 별도로 적용해야 한다. 쿼리 수의 감소율을 그대로 총 비용 감소율로 주장하지 않는다.

실제 Catalog metadata에서 events의 `__ingest_ts`에 대한 DAY 파티션을 확인했다. 발생 시각만으로 이 파티션이 잘린다고 가정하면 늦게 수집한 과거 사건을 잃는다.

두 종류의 쿼리 모두 원격 EXPLAIN이 HTTP 200으로 성공했다. 대상 선택 쿼리는 `payload_json`에서 sample ID/마감 시각을 추출하고 Window/Sort를 수행한다. 일반 track까지 들어 있는 사건 테이블을 반복 읽는 구조다. 원시 실행 계획은 `results/baseline-explain-{0,1}.json`에 있다.

## 구간 SQL 시험

동일 fixture를 저장소에서 귀속·정규화 합산하도록 한 단일 SQL 시험은 HTTP 200, 300표본, 보상 불일치 0이었다. 3,179ms, `bytes_scanned` 1,532,530, `files_scanned` 25, `r2_requests_count` 94였다. 기존 13쿼리 대비 스캔 바이트 감소는 약 35%이며, 단일 실행의 시간 차이를 일반적인 성능 보장으로 취급하지 않는다. 실제 LearningSource 연결 후 원격 재검증도 1쿼리·300표본·보상 불일치 0으로 통과했다. 해당 HTTP 실행은 4,242ms였고 스캔량·파일 수·R2 요청 수는 SQL 시험과 같았다. 이후 용량 초과 재시도 분류 변경은 로컬 테스트로 검증했으며 원격 alarm 재시도 검증은 남아 있다.

두 리뷰어가 발견한 반복 sample 문맥 충돌 검사를 추가한 최종 SQL도 원격 HTTP 200·300표본·불일치 0으로 통과했다. 이 검사로 스캔량은 1,800,198바이트(기준선 대비 약 24% 감소), 파일 수 27, R2 요청 수 106이 되었다. 위 35% 절감은 검사 추가 전 시험값이며 최종 수치로 사용하지 않는다. 최종 전체 HTTP 지연은 이후 부하 검증에서 다시 측정한다.

## Queue 묶음 처리

같은 ingest 호출 안의 일반 이벤트는 60,000바이트/100건 이내 메시지에 묶는다. 기존 SDK 한도 내 큰 이벤트는 단독 메시지로 보낸다. 호출 사이에 묶음을 기다리지 않는다. 작은 사건이 평균 k개씩 모이면 메시지 수가 대략 1/k로 줄지만, 실제 과금은 크기 단위·재시도·트래픽에 따라 달라진다. 원격 총비용과 요청 지연 비교는 아직 남아 있다.

타입 검사와 집중 테스트 8개가 통과했다. 두 독립 리뷰어가 기존 SDK 한도와의 불일치를 발견했고, 큰 이벤트의 단독 전송 및 형제 이벤트 보존 회귀 테스트로 수정한 뒤 두 리뷰어의 재확인을 받았다.

## 남은 검증

구간 단위 학습, projection 축소, 비동기 운영자 조회, 정책 신선도 설정, 파일 생성 간격을 구현하고 동일 fixture와 요청 부하로 비교해야 한다. 특히 분배 분모·신원 경계·0 보상·큰 음수/양수·분할·재시도 계약, 운영자 조회의 권한별 캐시 격리, 실제 데이터 반영 지연, p50/p95/p99 및 미참여율을 검증해야 한다.

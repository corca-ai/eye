# CSR·SPA 연동

[문서 안내](README.md) · [서비스 코드 구성](APPLICATION-INTEGRATION.md) · [서버 API](api/client.md#createeyebrowserserver)

브라우저는 `@eye/workers/browser`, 호스트 Worker는 `@eye/workers`를 사용한다. 브라우저 번들에는 Worker 바인딩이나 서버 secret을 넣지 않는다. React 등 프레임워크와 독립적인 첫 버전이며 UI 자동 감지·브라우저 goal 제출·범용 DOM 수집은 제공하지 않는다. 일반 track·구매 goal은 기존 서비스 수집 경로와 SDK를 사용한다.

## 연결 순서

1. 기존 설치 절차로 골·실험을 등록한다. 화면 코드와 같은 arm 목록을 사용한다.
2. 서비스 인증 경계에서 subject, browserBinding, scope를 구성한다.
3. [csr-server.ts](../examples/csr-server.ts)의 POST 준비·노출 경로를 연결한다.
4. 앱 시작 때 브라우저 클라이언트를 만들고, 실제 라우트 진입 때 뷰를 생성한다.
5. 변형이 실제 표시됐을 때만 expose를 호출한다. [완전한 라우트 예제](../examples/csr-browser.mjs)를 호스트 브라우저 빌드에 포함한다.

```ts
import { createEyeBrowser } from '@eye/workers/browser';
const eye = createEyeBrowser({ scope: authEpoch });
// 아래는 라우터의 실제 진입 시점. 렌더마다 beginView를 호출하지 않는다.
const view = eye.beginView();
const selection = view.variant({
  experimentId: 'checkout', variants: { standard: 'standard', compact: 'compact' }, fallback: 'standard',
});
renderCheckout(selection.value);
selection.expose(); // 로컬 큐 접수 여부. fallback은 false.
// 라우트 이탈: view.dispose()
```

variant는 동기 함수이며 네트워크를 기다리지 않는다. 미준비면 fallback으로 고정된 뷰를 만들고, 준비 요청을 타이머로 시작한다. 준비가 완료돼도 현재 뷰는 바뀌지 않으며 다음 뷰부터 적용한다. 준비는 한 번에 최대 20개를 묶고 최소 5초 간격으로 시작한다. prepare 실패 후 현재 뷰를 자동 재시도·교체하지 않고 다음 선택에서 다시 준비한다.

서버의 `prepare(ids, states)`는 정책 조회를 기다리는 명시적 API다. 브라우저가 보낸 이전 증표와 표본 문맥은 서버가 검증한다. 페이지 응답을 지연시키지 않으려면 별도 POST 경로에서 실행한다. 기존 데이터 로딩과 합치거나 초기 snapshot을 공급할 수도 있지만 그 경우 prepare의 대기 비용은 해당 서버 경로에 포함된다. 브라우저 initial snapshot은 해당 인증 scope의 최신 응답만 사용하며 공유 캐시에 저장하지 않는다.

## 신원과 증표

- subject: 서비스 인증에서 확정한 cid·uid. 클라이언트 JSON에서 받지 않는다.
- browserBinding: 호스트가 인증한 브라우저 식별값. 서명된 HttpOnly 쿠키 등을 사용하며 로그인 전환에도 유지한다. 단순히 임의의 cid 헤더를 신뢰하면 안 된다.
- scope: 로그인·로그아웃·계정 전환마다 바뀌는 **비밀이 아닌 인증 세대**다. 인증 토큰 자체를 보내지 않는다.
- receiptSecret: 최소 32 UTF-8 바이트의 서버 전용 secret. decision secret과 분리해서 설정한다.

증표는 AES-GCM으로 배정·원래 신원·사용자군 속성·바인딩·적용 기한을 암호화/인증한다. 사이트와 용도에 묶이며 브라우저는 내용을 해석하지 않는다. 발급·검증 때문에 별도 DO 원장을 만들지 않는다. 서버 receive는 원래 배정으로 expose를 호출하고 Queue 접수 완료까지 기다린다. 분석 반영 완료는 아니다.

인증 변경이 끝나면 `eye.setScope(newEpoch)` 후 새 뷰를 만든다. 늦은 이전 준비 응답은 버리고 이전 뷰의 새 노출도 막는다. 이미 큐에 들어간 이벤트는 원래 증표를 유지한다. 서버는 현재 uid와 다르더라도 같은 인증된 browserBinding의 유효한 과거 증표를 수락한다. 이렇게 로그아웃 직전 노출을 새 uid로 바꾸거나 무조건 버리지 않는다. browserBinding까지 바뀌거나 유실됐다면 과거 증표는 거절된다.

서명 증표가 실제 가시성을 증명하지는 않는다. HTTP 경로에는 기존 호스트 인증, 동일 Origin POST 검사, 허용 실험 목록, 본문 크기 제한을 적용한다. 예제가 이 경계를 보여주며 서비스의 기존 요청 제한 정책도 적용할 수 있다.

## 뷰와 시간

한 뷰의 experimentId·placement 조합은 한 선택이다. 반복 호출은 같은 핸들을 반환하며 expose의 이벤트 ID도 한 번만 생성한다. 독립된 표시 위치에는 다른 placement를 전달한다. 프리페치나 취소된 전환에서는 expose하지 않는다. UI 프레임워크의 재렌더·Effect 재실행과 무관하게 라우터가 뷰를 소유하게 한다.

적용 기한은 로컬 유지·관측 조건과 정책 유효기간으로 정한 시각이다. 기본 정책 설정에서는 최대 약 5분이다. 최초 표시가 기한을 넘으면 expose는 false이며 새 배정으로 바꿔 기록하지 않는다. 기한 안에 발생한 노출은 적용 기한 후 최대 5분까지 서버가 수락한다. 전달 유예가 배정 유지 기간을 연장하지 않는다.

브라우저 시각은 서버 snapshot 시각과 수신 후 경과 시간을 이용한 추정이다. 통신 지연만큼 오차가 있을 수 있고 실제 가시성 시각을 증명하지 않는다. 준비 요청의 왕복 시간만큼 적용 여유를 보수적으로 줄인다. 수신 이후에는 단조 시계와 벽시계의 경과 중 큰 값을 사용해 절전·시계 후퇴로 사용 기간이 무한히 늘어나지 않도록 한다. 서버는 미래 5초 초과·기한 밖 시각을 거절하며 5초 이내의 작은 미래 오차는 시각이 따라잡을 때까지 배치 재시도를 요청한다. 같은 사건의 occurredAt을 재시도마다 바꾸지 않는다.

현재 버전은 뷰에서 선택할 때 만료 또는 만료 임박 상태를 백그라운드 갱신한다. 장시간 열린 탭에 주기적인 노출·무조건 갱신 타이머를 넣지 않는다. 기존 화면은 유지하고 다음 라우트·문서·작업 진입에서 새 뷰를 만든다. 이미 기록한 노출의 보상은 기존 관측·귀속 계약을 따른다.

## 전송과 실패

노출 큐는 메모리에 최대 100개, 배치는 UTF-8 약 16 KB/최대 50개다. 기본 250ms에 전송하고 실패 시 3초 후 같은 payload로 총 3회 이내, 재시도 판단 시 큐 진입 후 60초 이내에서 재시도한다. 크기 초과·큐 포화·접수 거절·재시도 포기는 onError로 알린다. accepted:false 응답은 영구 거절로 보고 재시도하지 않는다.

flush는 진행 중인 전송에 합류하고 남은 배치를 제한된 재시도 정책 안에서 모두 처리한다. 실패한 이벤트를 무한히 기다리지는 않는다. 기본 전송은 10초 제한의 fetch와 keepalive를 사용한다. 실제 서비스의 전송 함수로 교체할 수도 있다. visibilitychange 때 flush를 호출하는 예제를 제공한다. 종료 시 전달은 최선 노력이며 sendBeacon을 영속 저장 확인처럼 취급하지 않는다. 첫 버전은 별도 Beacon 경로, 디스크 오프라인 큐, 다중 탭 조정을 넣지 않는다. 실패·차단·종료 때문에 유실될 수 있으므로 무편향을 보장하지 않는다. 사용자군/arm별 미참여와 수신 품질을 운영 환경에서 대조한다.

사용 중인 선택 캐시는 최대 1,000개다. 브라우저 prepare/send 콜백을 교체하면 응답 형식과 timeout·인증도 서비스가 책임진다. dispose는 다음 작업을 중단하며 이미 시작한 HTTP를 취소하거나 이미 접수된 이벤트를 취소하지는 않는다.

## 검증 범위와 비용

로컬 검증은 fallback의 동기 반환, 취소된 뷰·중복 노출, 전송 재시도 ID 유지, 인증 전환과 늦은 응답, 만료·변조·타 사이트/브라우저 증표 거절, 원래 uid 유지, Queue 실패 응답을 포함한다. 패키지 검사는 DOM 타입만 사용하는 외부 브라우저 프로젝트도 컴파일한다.

발급·수신의 암호 연산은 Worker 로컬 CPU다. 수신에는 기존 Queue와 학습 경로의 비용이 들며 무료 경로가 아니다. prepare는 정책 조회 API를 호출한다. 현재 문맥은 기본 sessionStorage에 보관하므로 같은 탭의 새로고침에서 이어갈 수 있다. storage 어댑터를 교체할 수 있으며 저장 불가·상태 유실 시 새 문맥을 쓴다. 탭 간 동기화는 없다. 정책 응답 대기 중 실제 노출이 문맥을 바꾸면 오래된 응답을 버리고 다시 준비한다. 이번 구현에 원격 부하·브라우저 실측 결과나 비용 절감률을 주장하지 않는다. 실제 서비스에서 테스트한 뒤 갱신 재사용을 추가 최적화한다.

# 서버 요청 경로의 수집 예산과 비용

2026-10-25. 기준 커밋 `53147d8`과 같은 입력을 비교했다. SDK의 동기 처리와 과부하 방어를 검사하며 실제 Cloudflare 응답 지연·p95/p99·CPU 과금 측정은 아니다.

## 동작

- 요청별 접수 건수·누적 추정 바이트·대기/전송 중 추정 바이트를 제한한다. 예산이 꽉 차면 사건 생성·검증 전에 `unavailable`을 반환하고, 다음 사건까지 더했을 때의 초과도 접수 전에 검사한다. `Submission.accepted`의 의미는 유지한다.
- 전송 중인 배치를 대기 바이트에서 빼지 않는다. 전송 시도가 끝나면 성공·실패와 무관하게 해당 바이트만 복구한다. 이미 전송한 사건의 참조는 대기 배열에서 제거하며, 배치 순서·실패 후 남은 배치 처리·flush의 reject를 유지한다. 전송 중 새 사건도 같은 예산으로 검사한다.
- 수집만 하면 요청별 배정 Map·함수를 만들지 않는다. 첫 배정/준비/실험 노출 또는 저장 토큰 복원 시 초기화한다. 잘못된 secret·정책 최신성 설정은 기존처럼 createEye에서 거절한다. 로그 전용 state()는 복원할 토큰이 없으면 빈 결과를 반환한다.
- 속성을 한 번 순회하며 키 수·문자열 길이·scalar 타입을 검사하고 복사한 뒤 정렬한다. 제한 초과는 전체 JSON 직렬화 전에 거절한다. 접수 후 원본 객체 수정의 영향을 받지 않으며 정확한 UTF-8 사건 크기 검사는 남긴다.

기본값은 [CollectionLimits](api/types.md#collectionlimits)를 따른다. 한도는 각 SDK 인스턴스에 적용하며 사이트 전체의 부하 제한이 아니다. `createEyeRequest`와 브라우저 서버 어댑터도 상속한 EyeOptions의 설정을 사용한다. 브라우저 클라이언트 자체의 메모리 큐·재시도 계약은 [CSR 문서](CSR.md)를 따른다. 사용자 콜백·입력 getter·호스트가 미리 만든 큰 객체의 비용이나 JS 엔진 자체의 키 열거 비용까지 제한하지 않는다.

속성 키 기본 상한 256은 새 제한이다. 기존의 고차원 속성이 필요하면 maxAttributeKeys를 늘릴 수 있고, 10,000키 입력의 전달·분할·재시도 회귀 검사도 명시적 설정으로 유지한다. 속성 문자열 기본 상한 100,000은 사건당 100KB 제한에 들어갈 수 없는 거대한 입력을 조기에 거절한다. maxEvents/maxBytes는 flush로 초기화하지 않는다. 대량 job은 명시적 한도와 처리 묶음별 인스턴스를 사용한다.

## 측정

[원시 결과](measurements/request-path-results.json)는 Node.js v24.22.1/macOS에서 한 번 워밍업 후 다섯 번 반복한 요청당 평균의 중앙값이다. 전송은 로컬 대체 구현으로 drain하며, 측정 구간은 SDK 생성과 동기 track 호출이다. 모든 접수 사건이 전달되는지도 확인한다. 아래 작은 시간 차이는 GC·JIT·실행 환경의 영향을 받는다.

| 요청 입력 | 이전 ms | 이후 ms | 접수 의미 |
| --- | ---: | ---: | --- |
| 작은 사건 1개 | 0.006365 | 0.002760 | 모두 접수 |
| 작은 사건 5개 | 0.009872 | 0.007887 | 모두 접수 |
| 작은 사건 100개 | 0.137398 | 0.135550 | 모두 접수 |
| 문자열 64KB 사건 1개 | 0.034313 | 0.031941 | 모두 접수 |
| 문자열 1MB 사건 1개 | 0.524419 | 0.004884 | 모두 거절; 전체 JSON 생성 회피 |
| 1,000회 호출, maxEvents=20 지정 | 1.357492 | 0.040748 | 이전은 옵션 미지원으로 1,000접수, 이후는 20접수·980거절 |

마지막 행은 서로 다른 접수 정책의 과부하 비교이며 같은 사건을 더 빠르게 전송한 결과가 아니다. 이미 준비된 작은 사건의 정상 경로보다 거대한 입력 거절·누적 대기량 제한이 주된 보호 효과다. 실제 서비스에서는 연동 전후 응답 시간과 Worker CPU를 따로 측정한다.

## 오류 통지와 수집 포장의 후속 개선

기준 `5e53d94` 이후에는 다음 두 반복 작업을 줄였다. 접수·오류 코드·공개 API는 유지한다.

- 요청 래퍼에서 onError가 없으면 거절마다 진단용 EyeError를 만들지 않는다. 훅이 있으면 기존처럼 사건별로 통지하며, 훅이 던진 예외도 요청에 전파하지 않는다. 오류 집계·샘플링은 추가하지 않았다.
- 수집 Worker가 파싱한 사건의 크기 검사와 Queue 포장을 한 경로로 합쳤다. canonical envelope당 JSON 직렬화·UTF-8 크기 계산을 2회에서 1회로 줄인다. SDK가 보내온 크기는 신뢰하지 않으며 사건당 100KB, 건당 여유 200바이트, 배치당 240KB·100건과 Queue 분할·순서를 유지한다. 전체 검사와 포장이 끝나야 sendBatch를 호출한다.

[원시 결과](measurements/error-and-size-results.json)는 같은 Node.js/macOS 환경에서 테스트와 별도로 측정했다. 한 번 워밍업 후 다섯 번 반복한 평균의 중앙값이다. 오류 측정은 요청당 1건 접수 후 200건 거절, 수집 측정은 로컬 parse/validation/packing이며 네트워크·Queue 전송은 제외한다.

| 로컬 작업 | 이전 ms | 이후 ms |
| --- | ---: | ---: |
| 직접 SDK, 200건 거절 | 0.015404 | 0.023158 |
| 요청 래퍼, 훅 없이 200건 거절 | 0.798299 | 0.029040 |
| 요청 래퍼, 카운터 훅으로 200건 거절 | 0.716680 | 0.677612 |
| 작은 사건 1개 수집 준비 | 0.002910 | 0.001538 |
| 작은 사건 50개 수집 준비 | 0.112475 | 0.058244 |
| 한글 20,000자 속성의 사건 2개 수집 준비 | 0.532995 | 0.199278 |

직접 SDK와 훅 있는 경로는 대조군이며, 이들의 작은 시간 차이를 개선·회귀율로 해석하지 않는다. 훅 없는 거절 경로에서 불필요한 객체 생성을 생략한 효과와, 같은 Queue 패킷을 만드는 반복 직렬화 감소를 확인했다. 수집 Worker의 절감은 백그라운드 CPU 작업 감소이며 실제 페이지 지연·Worker 과금 절감률을 뜻하지 않는다.

현재 측정 코드는 실제 packIngestion 함수를 호출한다. 모든 접수·거절·훅 통지 건수를 검사하며, 생성된 Queue 패킷을 기존 packEvents 결과와 비교한다. 회귀 검사는 UTF-8 경계·단독 대형 사건·배치 총량·한 번의 직렬화·잘못된 크기 정보 무시·거절 시 배치 전체 미전송을 포함한다.

[측정 코드](https://github.com/corca-ai/eye/blob/main/benchmarks/sdk/error-and-size.mjs)는 저장소 체크아웃에서 다음과 같이 실행한다.

```sh
npm run build
node benchmarks/sdk/error-and-size.mjs
```

# 증분 학습의 조회·알람 비용 개선

2026-10-25. 기준은 `4f68dcc0b3825a97e6e5ef7125b88dfa4f7e188d`다. 선행 [상태 최적화](STATE-OPTIMIZATION.md)의 배치 쓰기 결합·압축·성공 사전 캐시 이후에 남아 있던 반복 작업을 줄였다. 원본 재스캔 제거와의 비교가 아니다.

## 현재 방식

1. 동일 동기 트랜잭션의 goalId별 현재 정의를 한 번 읽는다. 마지막 변경 이후 발생분은 현재 상태를 사용하고, 더 오래된 사건만 기존 이력 조회로 판정한다. 최초 accepted/rejected 기록이 재시도 판정보다 우선한다. 다른 요청까지 캐시하지 않아 관리 변경을 즉시 반영한다. siteId도 최초 수집 때만 쓴다.
2. 속성 사전은 날짜·출처·키·타입으로 ID를 만들고 배치 중복/성공 캐시부터 확인한다. 필요한 객체와 payload JSON만 생성한다. 원본 속성 파싱·키 순회는 남으며, 원본 레코드와 성공 확인 뒤에만 캐시하는 규칙은 그대로다.
3. 정상 마감과 메타데이터 만료를 다음 60초 경계로 올려 합친다. 수신 허용 마감 `startAt + W + G`는 그대로다. 출력·통계 반영에 경계 정렬로 60초 미만이 추가될 수 있으며 실제 플랫폼·적체·실패 지연은 별도다. 한 번에 500표본/관측 출력 약 512KB, 정리는 테이블별 1,000행, outbox 전달은 20개까지다. 남은 기한 경과 작업과 outbox는 약 1초 뒤 이어 처리하고 실패 백오프는 유지한다. 빈 사이트는 주기적으로 깨우지 않는다.
4. 노출 갱신은 사용자·실험 참조 한 행만 읽는다. goal과 신원 이동은 필요한 전체 참조를 읽으며 배치 안의 이동·삭제·갱신을 보존한다. goal의 표본 조회는 기존 작은 definition에서 숫자만 추출한다. 큰 고정 속성은 노출 검증·문맥 갱신과 마감에만 읽는다.
5. 기본 대시보드는 `analytics.summaries.query`, 저장·자동 보고서는 명시적 `kind: 'summary'`로 선택할 수 있다. 기존 원본 보고서는 유지한다. 완료 UTC 시간, coverage, 특정 ID 조건을 지키며 원본 SQL로 자동 대체하지 않는다. 설정·코드 예제·결과 신선도는 [분석 계약](ANALYTICS.md#요약-기반-저장자동-보고서)을 따른다.

## 재현과 결과

```sh
npm run build
node benchmarks/incremental-cost/run.mjs --dist=dist --repeats=5 --output=/tmp/eye-cost-after.json
# 기준 revision도 별도로 빌드하고 같은 스크립트에 전체 dist 경로를 전달한다.
node benchmarks/incremental-cost/run.mjs --dist=/absolute/path/to/baseline/dist --repeats=5 --output=/tmp/eye-cost-before.json
node benchmarks/compact-state/run.mjs --repeats=5 --output=/tmp/eye-compact-after.json
```

전후를 동시에 실행하지 않고 순서대로 측정했다. Node v24.22.1, macOS arm64, 메모리 SQLite다. 원시 반복 측정·입력·소스/스크립트 해시는 `benchmarks/incremental-cost/results.json`에 보관한다. JSON 반환량은 SQLite 파일·페이지 읽기나 Cloudflare 청구 바이트가 아니다.

| 고정 입력 | 이전 | 이후 |
| --- | ---: | ---: |
| 같은 사용자 1/10/100/1,000실험 중 한 실험 재노출 시 참조 반환 행 | 1/10/100/1,000 | 모두 1 |
| 25KB 속성 표본에 goal 100개, 개별 호출: 표본 SELECT 결과 JSON 합 | 2,627,609B | 17,209B |
| 같은 goal 100개를 한 배치로 처리: 표본 SELECT 결과 JSON | 26,222B | 118B |
| 하루 10,000표본, 8.64초 간격: 모의 마감 alarm/cohort | 10,000 | 1,440 |
| 20개 고정 일별 키, track 10,000개: 사전 payload 생성 수 | 200,000 | 20 |
| 같은 사전 입력의 전송량 | 원본 10,000 + 사전 20행 | 동일 |

사전 실험은 100개씩 전송하며 성공 캐시가 유지된다. 1회 예열 후 5회 중앙값은 153.4 → 97.1ms였고 전송 레코드 digest가 동일했다. 생성 횟수 계측을 포함한 로컬 시간이다. 키 변경·여러 isolate·축출·실패가 있으면 효과가 줄어든다. 전송량은 선행 캐시 최적화에서 이미 줄었고 이번에는 불필요한 생성이 줄었다.

표본 보상은 큰 속성 유무·배치 크기·전후 모두 일치했다. 알람 실험은 지연·실패·적체가 없는 무보상 표본을 사용해 10,000개가 모두 닫혔음을 검사한다. 운영 알람 수가 항상 하루 1,440회 이하라는 보장은 아니다. 저트래픽은 원래 마감도 적으며 고트래픽·큰 속성은 한 번의 처리 한도를 넘어 추가 alarm이 필요하다.

별도 workerd 회귀 테스트에서 동일 goal 100개의 현재 정의 조회는 1회, 이력 조회는 0회였다. 이전 active/paused 사건과 최초 거절·수락 재전송은 기존 판정을 유지한다.

기존 compact-state의 입력 10,000개/표본 1,000개 workload는 보상 digest와 SQL 20,598호출·행 변경 9,503건이 전후 동일했다. 중앙값은 108.6 → 113.9ms로 이 작은 속성 입력에서 CPU 향상을 보이지 않았다. 좁은 SQL 추출과 캐시 관리도 비용이 있으므로 모든 입력의 처리 시간이 좋아진다고 해석하지 않는다. 요약 활성화는 9,525행 변경·5개 저장 버킷으로, 500개 학습 관측 조회가 2개 버킷을 읽는다. 자주 조회하지 않으면 요약 추가 쓰기가 이득이 아닐 수 있다.

실제 Cloudflare CPU·영속 디스크·인덱스 쓰기·네트워크·운영 청구액은 측정하지 않았다. 하루 총 사건 수만으로 절감액을 계산하지 않으며 노출/goal 비율, 속성 크기, 동시 실험 수, 배치 구성, 사이트 분산과 조회 빈도를 함께 측정해야 한다. 원본 저장·Queue 전달은 유지하며 60일 조회 제한도 원본 물리 삭제 정책이 아니다.

## 검증

회귀 검증은 과거 골 상태, 늦은 보상 거절, 빠른 backlog/outbox 후속 처리, 참조의 부분 읽기→전체 읽기, 보상 누적 후 전체 문맥 읽기, 사전 실패·동시 miss·축출, 요약 작업의 고정 페이지·UTC 경계·coverage 실패·SDK 경계를 포함한다. 전체 `npm run check`와 `npm run check:package`가 빌드·타입·테스트·생성 문서·외부 소비자·Worker dry-run을 검사한다.

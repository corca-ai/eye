# v2 비용 모델

이 문서는 로컬 배정·구간 마감·비동기 보고서 구조의 비용 계산 기준이다. [v1 추정](COST.md)의 월 $920–970을 현재 버전에 적용하지 않는다. 현재 증거는 [측정 기록](ISSUE-1-PERFORMANCE.md)에 있으며, 요청 부하시험과 동일 fixture 비교의 범위·한계도 함께 기록했다.

## 계산 범위

2026-10-24 공식 가격표, Workers Paid·R2 Standard, USD·세금 제외·30일 기준이다. 포함량은 계정 전체에서 공유한다. 기존 서비스에 Eye를 추가하는 비용에는 이미 처리하던 호스트 요청 요금을 다시 더하지 않고 추가 CPU만 더한다. 별도 HTTP 수집 요청, Queue consumer 호출, cron 등 실제 추가 과금 호출은 포함한다. Service Binding 호출은 Workers 요청 요금과 별개 규칙이므로 RPC 횟수를 모두 HTTP 요청처럼 계산하지 않는다.

아래 포함량 차감은 독립 계정의 견적에만 사용한다. 다른 서비스가 포함량을 소비했다면 남은 포함량으로 대체한다. 최소 과금 단위·반올림 때문에 연속 단가 계산과 실제 청구서는 차이가 날 수 있다. 특히 DO duration은 초과분을 백만 GB-s 단위로 올림하는 현재 문서를 따른다.

| 비용 항목 | 월 사용량 변수 | 포함량 / 초과 단가 |
|---|---|---|
| Workers 구독 | 계정 | $5/월 |

## 같은 workload를 비교할 때

예시로 월 3천만 사건, ingest 호출당 평균 작은 사건 3개, 월 마감 표본 300만 개, 마감이 720개 시간 구간에 균등하게 분포한다고 가정한다. 이 수치는 사용자가 확정한 운영 트래픽이나 실제 부하 결과가 아니다. 3실험에 매번 노출하는 페이지는 일반 track·골까지 함께 보내므로 페이지 수와 사건 수를 혼동하지 않는다.

- Queue: 이벤트별 메시지이면 9천만 작업, 3개 묶음이면 3천만 작업이다. 재시도·64KB 초과가 없고 포함량이 남았다면 $35.60 → $11.60/월이다. 수집 호출 간 이벤트를 기다려서 묶지 않으므로 실제 묶음 크기를 적용해야 한다.
- 학습: 이전 50표본 페이지의 대상/원본 두 쿼리와 마지막 빈 조회는 약 `720 × (2 × ceil(3000000/720/50) + 1) = 121680`쿼리다. 1000표본 구간 SQL은 약 `720 × ceil(3000000/720/1000) = 3600`쿼리다. 실제 시간별 분포, 정확히 가득 찬 페이지의 종료 확인, 용량 축소·재시도·빈 시간 구간에 따라 달라진다.
- 운영자 조회: 월 1만 번의 동일 기본 보고서 조회가 시간별 저장 결과로 충분하다면 원본 계산은 1만 → 최대 720회로 줄일 수 있다. 사용자별 권한·필터·기간이 다르면 공유할 수 없고, 상태 폴링·R2 페이지 읽기는 계속 과금된다.
- SQL의 10MB 최소 과금만 적용한 학습 비교는 약 $3.02 → $0.07/월이다. 즉 쿼리 수가 크게 줄어도 원래 스캔이 작으면 SQL 절감액은 작다. 실제 스캔이 평균 1GB라면 같은 쿼리 수에서 약 $304.18 → $8.98이지만, **양쪽 평균 1GB라는 가정 자체는 측정값이 아니다.** 최종 계산은 각 쿼리의 실제 스캔량을 합쳐야 한다.

원본 반복 스캔 감소 외에 R2 GET·Catalog metadata 작업, Worker/DO에서 결과를 처리하는 시간도 줄 수 있다. 반대로 고정 결과 PUT/GET, 비동기 작업의 SQLite 상태와 alarm이 추가된다. 이 항목들을 제외한 SQL 단독 절감률을 총 비용 절감률로 부르지 않는다.

## 전송·파일·보관 가정

동일 fixture 인코딩은 원본 5,165사건당 9,431,653 → 7,111,389바이트였다. 이 비율을 월 3천만 사건에 단순 적용하면 약 54.8 → 41.3GB지만, 속성 크기·중복 사전·Queue batch 구성·완료 관측 export에 따라 달라진다. 작은 합성 fixture의 Parquet 압축률로 운영 저장량을 예측하지 않는다.

설치의 fan-out SQL에는 테이블별 INSERT가 있다. 모든 입력을 각 변환에서 다시 처리하는 과금인지에 따라 `P`가 stream 입력보다 커질 수 있다. **Stream ingress가 무료라는 사실은 SQL 변환이 무료라는 뜻이 아니다.** 전체 변환의 처리량을 사용하며 미계측 상태에서는 입력 1배와 INSERT 수 배를 민감도 범위로 계산한다. sink는 필터 후 출력의 합계를 사용한다.

300초 rollover는 파일·metadata 생성 빈도를 낮춘다. 실제 비교에서 events append 파일은 4 → 1개였지만 이를 전체 Class A/Catalog 비용의 75% 감소로 일반화하지 않는다. Compaction은 추가 읽기/쓰기와 snapshot 보관을 발생시키며, 이미 활성화된 테이블에서 별도로 계측해야 한다.

최근 60일 조회 제한은 원본의 물리 삭제 기능이 아니다. 별도 보관 정책이 없으면 원본·snapshot 저장량은 계속 증가하므로 `Rs`를 항상 두 달치라고 가정하지 않는다. 마감 고정 결과는 성공 후 지우고, 실패한 작업의 잔여 객체는 lifecycle이 정리할 수 있다. 보고서 결과의 보관은 최대 49시간이고 관련 lifecycle은 최소 3일을 확보한다. 기존 원본 파일에 임의 lifecycle을 걸어 Iceberg 테이블을 손상시키지 않는다.

## 총액을 계산하는 명시적 예시

아래는 위 월 3천만 사건·300만 마감 표본 시나리오의 **계산 예시**다. 실제 계정 청구서 예측이나 부하시험에서 관측한 월 사용량은 아니다. 비교 기준은 v2 최적화 전이며 v1 중앙 원장 모델과 비교하지 않는다. 새 설계에서 메시지당 평균 2개를 가정해, 위 3개 묶음 예시보다 보수적으로 계산한다.

| 추가 가정 | v2 최적화 전 | 최적화 후 |
|---|---:|---:|
| Queue 과금 작업 | 9천만 | 4,500만 |
| 완료 관측·사전 등을 포함한 비압축 export | 60GB | 45GB |
| 모든 Iceberg sink의 비압축 출력 합계 `S` (별도 가정) | 60GB | 45GB |
| 변환 처리량 민감도 | export의 1–7배 | export의 1–7배 |
| 학습 + 기본 보고서 SQL 실행 | 121,680 + 10,000 | 3,600 + 720 |
| R2 평균 저장량(보관 정책을 별도로 적용한 가정) | 40GB-month | 30GB-month |
| R2 Class A / Class B | 100만 / 660만 | 30만 / 50만 |
| Catalog 작업 | 50만 | 20만 |
| Compaction 읽기+재작성 / 객체 수 | 100GB / 50만 | 75GB / 20만 |
| Workers CPU(호스트 기본분 제외) | 6천만 ms | 4천만 ms |

Workers 추가 과금 요청은 1천만 이하, DO 호출 100만 이하·활성 40만 GB-s 이하·쓰기 5천만 행 이하·읽기 250억 행 이하·저장 5GB-month 이하라고 가정한다. 진단 로그도 포함량 안으로 가정한다. 이런 항목의 사용량을 0으로 가정한 것이 아니라 **포함량 안**으로 가정한 것이다. 이 가정을 넘으면 첫 표의 비용이 추가된다. 기존 서비스의 요청/CPU가 같은 계정의 포함량을 소비했다면 아래 총액을 그대로 사용할 수 없다.

| SQL 평균 과금 스캔량 가정 | v2 최적화 전 총액 | 최적화 후 총액 |
|---|---:|---:|
| 양쪽 모두 최소 과금 10MB/쿼리 | 약 $46–61/월 | 약 $24–34/월 |
| 양쪽 모두 평균 1GB/쿼리 | 약 $372–387/월 | 약 $34–45/월 |

각 범위는 fan-out 변환 처리량의 1–7배 민감도이며 신뢰구간이 아니다. Workers 구독 $5, CPU, Queue, Pipeline, R2 저장/작업, Catalog, compaction, SQL을 합했다. 비동기 보고서와 마감 결과의 저장·읽기도 R2 가정에 포함된다. 원본 데이터가 계속 쌓이거나 ad hoc 조회가 늘면 범위를 넘을 수 있다.

예를 들어 10MB 시나리오에서 Queue만 $35.60 → $17.60, SQL은 $3.27 → $0.08이다. 큰 총액 차이는 SQL 평균 스캔 가정에 민감하므로 작은 fixture의 24% 스캔 감소를 운영 규모에 그대로 곱하지 않는다. 실제 도입 견적에서는 위 사용량 열을 실제 사건 크기·페이지별 쿼리·파일 수·보관 정책으로 교체한다.

## 실제 요청 시험에서 관측한 사용량

최신 200 RPS·5분 Eye 시험의 측정 창에서 호스트 CPU는 약 149.82초/59,916계측 요청(평균 2.50ms), private Worker CPU는 약 120.48초였다. private Worker 호출에는 RPC가 포함되므로 호출 수를 그대로 Workers 과금 요청 수로 바꾸지 않는다. 같은 창의 DO 활성 시간 합계는 약 8.43GB-s, SQLite 읽기 8,100행·쓰기 0행이었다. 이 시험의 관측 기간은 7일이므로 완료 학습의 쓰기 비용을 측정한 값이 아니다.

Queue 집계는 write/read/delete 각각 82,736/80,258/75,706 과금 작업, 관측 평균 재시도 0이었다. R2는 PutObject 29, multipart 시작/part/완료 9/11/11, GetObject 9회였고 Catalog는 load-table 30·update-table 11회였다. maintenance 데이터는 빈 결과였으며 장기 compaction 비용이 없다는 의미는 아니다. 이 수치는 해당 테스트 bucket/warehouse와 시간 창의 Adaptive 집계다. 전송·소비·파일 commit의 시간 경계가 달라 사건 수와 완전히 일치하지 않으며, Pipeline sink 출력도 전송보다 늦게 집계될 수 있다. 이를 그대로 월간 완결 처리량으로 외삽하지 않는다.

부하 시험의 실제 요청당 비용과 마감/조회 비용은 서로 다른 workload로 분리해 측정했다. 학습 fixture의 13→1쿼리, 스캔 2,358,592→1,800,198바이트와 같은 전후 결과는 [측정 기록](ISSUE-1-PERFORMANCE.md)을 따른다. 위 월 총액 표는 이러한 구조를 적용하는 명시적 사용량 시나리오이며, 5분 시험을 한 달로 늘린 실측 견적은 아니다.

# DO 동작 점검과 수정 — 2026-10-23

[수정 전 부하테스트](LOAD-TEST-2026-10-23.md)의 지연과 Queue 적체를 Cloudflare 장애로 단정하지 않고, 공식 동작 계약과 코드의 저장·RPC 경계를 다시 점검했다. 아래 변경은 아직 커밋하지 않은 작업 트리 기준이다.

## 공식 동작에서 확인한 사항

- 동기 SQLite/KV API를 사용해도 영속화 비용이 사라지지 않는다. output gate는 미완료 저장이 있으면 외부 메시지와 응답을 기다리게 한다. 따라서 쓰기 → RPC → 쓰기 → RPC를 반복하면 복제 대기를 늘릴 수 있다. [Cloudflare의 input/output gate 설명](https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/)
- SQL cursor는 `await` 전에 소비해야 한다. 외부 I/O 대기 중 다른 요청이 상태를 바꿀 수 있으므로 재진입 후 revision 확인과 조건부 삭제가 필요하다. [SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- DO당 alarm은 하나이며 외부 I/O를 기다릴 때 일반 요청이 실행될 수 있다. 네이티브 alarm 실패 재시도는 무한하지 않다. [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- Workers의 `Date.now()`와 `performance.now()`는 I/O 뒤에 진행한다. 순수 로컬 결정 구간의 0ms 측정으로 실제 CPU 비용이 0이라고 판단할 수 없다. [Performance API](https://developers.cloudflare.com/workers/runtime-apis/performance/)

## 코드 수정과 회귀 검증

1. **Subject별 즉시 통계 발행 제거.** Subject는 변경을 shard에 적용하고, 중앙 Experiment에 대한 snapshot 발행은 shard alarm이 합친다. dirty 변경은 성공한 마지막 발행 후 60초 동안 누적한다. 여러 사용자가 같은 shard를 갱신해도 사용자마다 중앙 발행하지 않음을 테스트했다. 통계 반영은 이 간격과 Queue·처리 지연을 포함하며 엄격한 60초 SLA는 아니다.
2. **학습과 raw 분석 전송 분리.** 한쪽 실패가 다른 쪽의 전송·확인을 막지 않게 한다. 학습 적용 성공분은 RPC 사이마다 삭제하지 않고 모아서 revision 조건부 삭제한다. 실패분은 outbox에 남아 재시도하며 다른 revision을 삭제하지 않는다. shard 실패 중 raw export가 빠지고 복구 후 학습이 완료되는 검사를 추가했다.
3. **영속 alarm 재시도.** 실패 횟수·다음 시각을 저장하고 2초부터 최대 5분까지 지수 백오프와 객체별 jitter를 적용한다. 새 이벤트가 재시도 시각을 앞당기지 못한다. 외부 I/O 전 복구용 alarm도 예약한다. 저장소 자체가 불능인 경우까지 애플리케이션 재시도로 해결된다는 보장은 없다.
4. **불필요한 배정 보호 기간 축소.** 모든 발급 토큰이 확인된 관측 종료 이내에 만료되면 보수적 보호를 실제 종료로 줄인다. 종료 이후에도 유효한 미보고 노출 토큰이 있으면 기존 보호를 유지한다. 늦게 도착한 더 이른 노출 때문에 중단된 관측을 현재 관측으로 잘못 읽는 문제도 수정했다.
5. **토큰도 SWR 갱신.** 유효 토큰은 현재 요청에서 사용하고 만료 전에 다음 요청용 준비를 시작한다. 고정 관측 종료 때문에 연장이 불가능하면 다음 갱신을 만료까지 미뤄 반복 준비를 억제한다. 갱신 RPC가 해결되지 않아도 현재 결정이 반환되는 테스트를 추가했다.

앞선 수정의 분석 `fetch` receiver 바인딩·redirect 처리, shard snapshot 시각 정렬도 포함한다. 전체 `npm run check`는 14개 파일 **106개 테스트**와 타입·빌드·생성 API 문서 검사를 통과했다.

## Eye를 분리한 실제 DO 프로브

별도 Worker에는 Eye·Queue·Pipeline binding이 없다. `/none`은 DO 없이 응답, `/memory`는 저장 호출 없는 DO RPC, 나머지는 별도 DO 클래스의 KV 또는 SQL 읽기·카운터 쓰기다. 각 10 req/s, 30초, 사용자 20명, 4KB 응답, 10초 HTTP timeout으로 순차 실행했다. 아래 시간은 로컬 부하 발생기에서 측정한 네트워크 포함 ms다.

## 수정 후 측정 방법

호스트가 매 페이지마다 수행하던 세션 DO 조회를 제거한 `/fast-page`를 추가했다. 로컬 클라이언트 프록시가 브라우저별 signed token을 보관하고 별도 `/prepare` 요청으로 갱신한다. 이는 SDK 내부 전역 사용자 캐시가 아니다. baseline과 Eye를 같은 프록시로 통과시키며 준비 요청은 페이지 RPS와 별도로 집계한다. 이 경로는 토큰을 즉시 전달하는 호스트 연동의 검증이며, 기존 서버 세션 경로의 지연을 해결했다고 주장하지 않는다.

새 사이트·동일 사용자 풀 400명·신규 비율 5%·실험 3개를 사용한다. 관측 경계와 저장 지연을 분리하기 위해 세 실험 모두 관측 7일·최소 유지 1일이다. 따라서 2분 관측 실험의 경계 참여율이나 장기 학습 수렴을 검증하는 부하는 아니다. 10 req/s 준비 2분 → baseline 1분 → Eye 10 req/s 2분 → 100·200 req/s 각 1분으로 확인하며, HTTP 오류/누락 게이트를 통과하지 못하면 다음 단계로 확대하지 않는다.

결과와 잔여 검증은 아래에 기록한다. 원시 k6 summary·로그는 무시되는 `benchmarks/cf-load/results/`에 보관한다. 이 단기 확인은 당초 요청한 각 5분의 100·200 req/s 지속 부하 검증을 대신하지 않는다.

이 실행은 HTTP 지연과 백그라운드 지연을 분리했지만 **실험 참여율 목표는 미달**이다. 준비 완료 후에만 측정을 시작하는 게이트가 없고, 준비 요청을 4개로 제한한 클라이언트에 대기열이 쌓였다. 종료 시 준비 성공 416건·실패 17건·대기 및 실행 중 1230건·생성된 사용자 상태 1508개였다. 이 수치는 완료된 준비 요청 기준이며 시도 수나 준비된 사용자 비율과 같지 않다. `/prepare`는 실험 3개의 준비를 묶어 반환한다. 신규 요청은 모두 첫 요청에서 미참여했으며, 재방문 미참여도 충분히 줄이지 못했다.

HTTP 게이트는 참여율과 Queue 안정성을 검사하지 않는다. 이 실행을 처리 용량 합격으로 간주하면 안 된다. 수정 후에도 Queue 적체가 관찰됐다. 부하 종료 뒤 프록시를 중지하고 Queue·DLQ를 추가 관측했다. 원시 측정에서 검증하지 않은 개별 이벤트 무손실이나 장기 정상 처리를 주장하지 않는다.

### 독립 리뷰

두 명이 전체 변경을 독립적으로 검토했다. 한 리뷰에서 구버전 `lease-pin`을 항상 `토큰 만료 + W`로 해석하는 업그레이드 오류를 발견했다. 구버전은 확인된 관측 종료를 pin으로 쓰기도 했다. 구버전 pin과 `이관 시각 + 5분` 중 작은 값을 기존 발급 토큰의 만료 상한으로 한 번 저장한 뒤 pin을 줄이도록 수정했다. 지연된 더 이른 노출과 아직 유효한 구버전 토큰이 함께 있는 회귀 테스트는 수정 전 실패, 수정 후 통과했다. 위 원격 부하는 이 이관 전용 수정 직전 코드이며, 기존 상태 이관을 원격 검증한 결과는 아니다.


종료 후 첫 관측은 Queue 32,876건이었고, 종료 약 135초 뒤 0, 이후 관측에서도 0이었다. DLQ는 이 기간 0이었다. 이 수치는 best-effort 지표이며 순간 최대 backlog를 측정한 것은 아니다. 최종 이관 수정도 테스트 Worker에 `cf deploy`로 배포했다(버전 `4652e825-d6eb-4017-9a0a-b09d14132d22`).
